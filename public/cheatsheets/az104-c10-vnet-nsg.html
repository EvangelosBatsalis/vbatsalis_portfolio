Lesson 130 · 17.1

Virtual Networks (VNets)

A Virtual Network (VNet) is your isolated private network in Azure — equivalent to an on-premises network segment. Resources in the same VNet can communicate by default.

  • Address space: One or more CIDR ranges (e.g., 10.10.0.0/16)
  • Region-bound: VNet belongs to one region — resources in same VNet must be in same region
  • Subnets: VNet divided into subnets — each subnet is a range within VNet address space
  • No overlapping: Peered VNets cannot have overlapping address spaces
  • VNet-to-VNet: By default, VNets are isolated — use Peering or VPN Gateway to connect
# Create VNet with two subnets
az network vnet create \
  --name VNet-Production-GR \
  --resource-group RG-Network-GR \
  --location westeurope \
  --address-prefix 10.10.0.0/16 \
  --subnet-name Subnet-Servers \
  --subnet-prefix 10.10.1.0/24

az network vnet subnet create \
  --name Subnet-DMZ \
  --resource-group RG-Network-GR \
  --vnet-name VNet-Production-GR \
  --address-prefix 10.10.2.0/24
Realistic ScenarioSeptona Azure Network Architecture

VNet-Production-GR: 10.10.0.0/16
├── Subnet-Servers: 10.10.1.0/24 (VMs, app servers)
├── Subnet-DB: 10.10.2.0/24 (Azure SQL, no public internet)
├── Subnet-Management: 10.10.3.0/24 (Bastion, jump hosts)
├── AzureBastionSubnet: 10.10.255.0/26 (required name, /26 min)
└── GatewaySubnet: 10.10.254.0/27 (required name for VPN GW)

Αυτό αντιστοιχεί στο FortiGate VLAN setup που χρησιμοποιείς στο Septona on-prem!

Lessons 136–137 · 18.1

VNet Peering

VNet Peering connects two VNets — traffic flows via Azure backbone (not internet). Low latency, high bandwidth.

Local Peering

  • Same region
  • Very low latency
  • No gateway required
  • Free data transfer

Global Peering

  • Different regions
  • Low latency
  • Cross-region charges
  • No gateway required
🎯
Peering is NON-TRANSITIVE:
VNet-A peered with VNet-B. VNet-B peered with VNet-C.
VNet-A CANNOT reach VNet-C automatically!
Need: A↔C direct peering OR hub-spoke topology with gateway transit.

Peering requirements: No overlapping address spaces. Both directions must be configured. 
# Peer VNet-GR ↔ VNet-BG (must create both directions)
az network vnet peering create \
  --name GR-to-BG \
  --resource-group RG-Network-GR \
  --vnet-name VNet-Production-GR \
  --remote-vnet /subscriptions/BG-SUB-ID/resourceGroups/RG-Network-BG/providers/Microsoft.Network/virtualNetworks/VNet-Production-BG \
  --allow-vnet-access

az network vnet peering create \
  --name BG-to-GR \
  --resource-group RG-Network-BG \
  --vnet-name VNet-Production-BG \
  --remote-vnet /subscriptions/GR-SUB-ID/.../VNet-Production-GR \
  --allow-vnet-access

VNet Gateway (Azure-to-Azure)

VNet Gateway provides encrypted connectivity between VNets or between Azure and on-premises via IPSec/IKE tunnels.

TypePurposeProtocol
VPN GatewayEncrypted tunnel via internetIPSec/IKE
ExpressRoute GWPrivate dedicated connectionBGP (no internet)

VPN Gateway vs VNet Peering

VNet PeeringVPN Gateway
LatencyLowerHigher (encryption overhead)
BandwidthHigherLower (GW dependent)
CostCheaper (data transfer)GW hourly + data
Transitive❌ No✅ Yes (gateway transit)
Cross-subscription✅ Yes✅ Yes
On-premises❌ No✅ Yes (S2S VPN)
🎯
Gateway Transit: Hub-spoke topology. Hub VNet has VPN GW. Spoke VNets peer with hub and enable "Use Remote Gateway" — spokes can reach on-premises through hub's gateway. This IS transitive via gateway.

Lessons 141–143 · 19.1

Azure DNS

Public DNS Zones

  • Host your domain's DNS records in Azure (NS records at registrar)
  • Create: Portal → DNS Zones → Create → enter domain name (e.g., septona.gr)
  • Azure gives you 4 name servers — update at domain registrar
  • Add A, CNAME, MX, TXT records as needed

Azure-Provided DNS

By default, VNet uses Azure DNS (168.63.129.16) which resolves:

  • Public DNS (internet names)
  • VM hostnames within same VNet (FQDN: vmname.internal.cloudapp.net)
  • NOT across peered VNets unless using Private DNS Zones

Lesson 142 · 19.2

Private DNS Zones

Private DNS Zones allow custom DNS name resolution within VNets without exposing to internet.

# Create private DNS zone
az network private-dns zone create \
  --resource-group RG-Network-GR \
  --name septona.internal

# Link to VNet (enable auto-registration)
az network private-dns link vnet create \
  --resource-group RG-Network-GR \
  --zone-name septona.internal \
  --name Link-VNet-Production-GR \
  --virtual-network VNet-Production-GR \
  --registration-enabled true

# With registration=true, VMs in VNet auto-register their hostnames
# SRV-APP-GR-01 → srv-app-gr-01.septona.internal
💡
Auto-registration: Enable on at most 1 VNet per private zone. Can LINK (without registration) to up to 1000 VNets. VMs auto-register A and PTR records when auto-registration enabled.

Network Security Groups (NSG)

NSGs contain security rules that allow or deny inbound/outbound network traffic. Applied at subnet or NIC level.

NSG Rule Properties

PropertyOptions
Priority100–4096 — lower number = processed first
Source/DestinationAny, IP/CIDR, Service Tag, ASG
ProtocolAny, TCP, UDP, ICMP
PortSingle, range (80-443), * for any
ActionAllow or Deny
DirectionInbound or Outbound

Default Rules (cannot delete)

RuleDirectionWhat it does
AllowVnetInBound (65000)InboundAllow traffic from VNet
AllowAzureLoadBalancerInBound (65001)InboundAllow from Azure LB health probes
DenyAllInBound (65500)InboundDeny all other inbound
AllowVnetOutBound (65000)OutboundAllow to VNet
AllowInternetOutBound (65001)OutboundAllow to internet
DenyAllOutBound (65500)OutboundDeny all other outbound
🎯
NSG Dual-Level = AND Logic:
NSG on Subnet AND NSG on NIC = BOTH must allow traffic for it to pass.
If Subnet NSG allows port 443 but NIC NSG denies it → traffic is DENIED.

Standard LB: Closed by default. Must add NSG rule to allow inbound.
Basic LB: Open by default.

Service Tags

Pre-defined groups of IP ranges maintained by Microsoft — simplify rules:

  • Internet — all public IP space
  • VirtualNetwork — VNet + peered VNets address space
  • AzureLoadBalancer — LB health probe IPs
  • Storage — Azure Storage service IPs (region-specific: Storage.WestEurope)
  • Sql — Azure SQL IPs
  • AppService — App Service outbound IPs
# Allow HTTPS from internet to web servers
az network nsg rule create \
  --resource-group RG-Network-GR \
  --nsg-name NSG-WebServers \
  --name Allow-HTTPS-Inbound \
  --priority 100 \
  --direction Inbound \
  --source-address-prefixes Internet \
  --destination-port-ranges 443 \
  --protocol Tcp \
  --access Allow

# Deny all from internet to DB subnet
az network nsg rule create \
  --resource-group RG-Network-GR \
  --nsg-name NSG-Database \
  --name Deny-Internet-Inbound \
  --priority 200 \
  --direction Inbound \
  --source-address-prefixes Internet \
  --destination-port-ranges '*' \
  --access Deny

Lesson 148 · 20.2

Application Security Groups (ASG)

ASGs let you group VMs by application role and use those groups in NSG rules — instead of managing IP addresses.

# Create ASGs for application roles
az network asg create --name ASG-WebServers --resource-group RG-Network-GR
az network asg create --name ASG-DatabaseServers --resource-group RG-Network-GR

# Associate VM NIC with ASG
az network nic ip-config update \
  --resource-group RG-Network-GR \
  --nic-name SRV-WEB-01-NIC \
  --name ipconfig1 \
  --application-security-groups ASG-WebServers

# NSG rule using ASG (instead of IP addresses)
az network nsg rule create \
  --resource-group RG-Network-GR \
  --nsg-name NSG-Production \
  --name WebToDb \
  --priority 100 \
  --source-asgs ASG-WebServers \
  --destination-asgs ASG-DatabaseServers \
  --destination-port-ranges 1433 \
  --access Allow
✅
ASG benefit: When you add a new web server VM, just associate its NIC with ASG-WebServers — automatically inherits all NSG rules. No IP changes needed in rules. Scales cleanly to 100s of VMs.

Quiz — VNets, DNS & NSG

◈ Q01
VNet-A peered με VNet-B. VNet-B peered με VNet-C. Μπορεί το VNet-A να communicate με VNet-C;
  • A) Ναι — peering is transitive
  • B) Όχι — peering is non-transitive
  • C) Ναι, αλλά μόνο σε same region
  • D) Εξαρτάται από NSG rules
✅ B — Non-transitive. VNet Peering is NOT transitive. A↔B and B↔C does NOT give A↔C. You need direct A↔C peering OR gateway transit through a hub VNet.
◈ Q02
/29 subnet — πόσα IPs μπορούν να χρησιμοποιηθούν για VMs;
  • A) 8
  • B) 5
  • C) 3
  • D) 6
✅ C — 3 usable. /29 = 8 total IPs − 5 Azure reserved (.0 network, .1 gateway, .2-.3 DNS, .255 broadcast) = 3 usable for VMs.
◈ Q03
Traffic ΔΕΝ φτάνει σε VM. Subnet NSG allows port 443. NIC NSG: no rule for 443. Τι γίνεται;
  • A) Traffic allowed — Subnet NSG αρκεί
  • B) Traffic denied — NIC NSG default deny applies
  • C) Traffic allowed — inbound VNet rule allows it
  • D) Εξαρτάται από priority
✅ B — Denied. Dual-level NSG = AND logic. Subnet NSG allows 443, but NIC NSG has no allow rule → default deny applies at NIC level → traffic denied. Both levels must allow for traffic to reach the VM.
◈ Q04
Ποιο subnet name είναι ΑΠΑΙΤΗΤΟ για deployment Azure VPN Gateway;
  • A) VPNGatewaySubnet
  • B) AzureVPNSubnet
  • C) GatewaySubnet
  • D) AzureGateway
✅ C — GatewaySubnet. Exact name "GatewaySubnet" is required. Minimum /27 size. Cannot deploy VPN Gateway to any other subnet name. Similarly, AzureBastionSubnet is required for Bastion.
